## What exists versus what must work

### Startup, login and agent selection

The app already has a connection chooser, separate Cloud identity and agent target, remote pairing, secure Android token storage and offline mode. The local-development target and mock mode are present only in `ELIZA_DEV_ALLOW_TEST_MOCKS=1` builds. `apps/app/src/runtime/{alpha-client,connection-ui,remote-protocol,cloud-protocol}.ts*` and `AlphaConnectionPlugin.java` own much of this product-local implementation. Real local Cerebras conversations and owner-bound actions have passed focused tests. The Cloud path currently rejects the verified device-action/workflow target used by remote mode, so successful Cloud chat would not establish parity. The Cloud callback has produced invalid/expired-session behavior; live Gmail authorization has returned token-exchange 401. A running enclave health check proves availability only. The latest combined runtime is not the deployed enclave revision.

Required journey: boot into Alpha HOME; choose Cloud or remote; authenticate normally; list the current owner's agents; choose an existing agent or explicitly create one; pair exactly that agent; start a conversation; background, reconnect and restart without crossing owners or duplicating replies. Revoked/expired credentials return to recovery without deleting unrelated notes. Mock/offline/local-development states must never impersonate a Cloud login. Cloud enrollment and credit setup remain operational gates. Enclave hosting is no longer the agent architecture (October 1 resident-agent decision).

### Chat and navigation

The prototype chat geometry and retained-view context are implemented. Agent-adapter code builds per-view context and mediates native approvals. Focused all-view Cerebras tests and native note/reminder/settings actions exist, but the latest combined full session has failed before completing every step. There is no blanket latest-build end-to-end pass.

Required: typed and spoken open/switch requests resolve only enabled MVP capabilities; one conversation retains history and context across app changes; cancellation stops transport/playback and prevents late effects; interrupted streams recover once using durable message/run IDs. A failed or ambiguous mutation shows its actual status and offers receipt recovery, not a new automatic attempt. The agent must ask for missing task details rather than infer a recipient, calendar, time zone or destructive target from prototype fixtures. Disabled features must disappear from discovery, suggestions and deep links, not just the home grid.

### Voice, transcription and latency

Current phone recording and playback use native audio, but much of the verified ASR/TTS computation is on a paired Mac host using Whisper/Kokoro. `AlphaVoiceCloudPlugin.java` hardcodes provider route/format assumptions; `runtime/paired-voice.ts` and `prototype/voice-adapter.ts` manage selection and lifecycle. This is not proof of on-device inference. One real host round-trip recognized the complete test phrase, but recorded synthesis and ASR timings exceeded the six-second simple-query target. Synthetic AAC input does not prove physical microphone, echo, interruption or Bluetooth behavior.

Recommendation: keep capture/playback in a reusable native voice plugin; expose speech-engine capabilities and an explicit local/remote route. Android offers on-device recognition only when an installed engine supports it; check availability rather than assuming AOSP contains an engine. TTS similarly requires a qualified installed voice. A current package-manager query on the test AOSP emulator found neither a recognition service nor a TTS service; the image needs explicit engine provisioning. See [SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer) and [TextToSpeech](https://developer.android.com/reference/android/speech/tts/TextToSpeech). Qualify a licensed engine/model on the exact image if the platform engine is unavailable.

Required: permission at use, visible recording state, Stop/Cancel, transcript review/correction, save into an actual note, playback controls, silence/no-speech/denial handling, background cancellation and late-response rejection. Record language, engine/model and route provenance. Voice does not auto-send for now (owner decision, October 7): the user reviews the transcript and sends, so a hands-free six-second round trip cannot be met as written. Open follow-up [A-10](decisions.md#open-decisions) chooses between excluding the user's review/send time from the measurement and revisiting the target. Proposed latency method: end-of-user-speech to first audible agent response, with end-to-end completion separately recorded, cold/warm runs and network conditions retained. Use the DoD's six seconds as the acceptance target; the percentile and sample count are proposed in the plan, not silently invented contractual terms.

### Notes and selected content

On Android, text Notes live in the native Keystore-backed secure store (`notes-records:v1:device`), migrated once from the earlier renderer `localStorage` value; the web build (a development/preview surface) keeps browser-local, unencrypted Notes. Audio/transcript files are private native files. Native document import/export, exact bytes, activity/process recreation and selected-note revision checks have useful focused evidence. There is no general synchronized Notes service, and private storage alone does not establish end-to-end encrypted sync. The newly applied workflow bridge can retain an encrypted read result before uploading a receipt; native and whole-host-phone acceptance are still open.

Required: create/read/edit/delete; deleted notes, including voice notes and their recordings, go to a durable Trash that empties automatically 3 days after deletion, with Undo, Restore, Delete forever and Empty Trash (decision P-06; see [browser storage](browser-storage.md#notes-trash)); voice-to-note and note-to-speech; exact note identity and revision; restart recovery; save failure must preserve the draft. Selected-note reads require clear scope, and returned content must not accidentally include unselected notes. A note changes once after a confirmed agent action; uncertain upload must replay the stored receipt, not reread a now-changed note. Move generic note records/revisions/attachments and agent actions upstream. Keep the Alpha editor layout and labels local. Avoid building a second unrelated note store for digests.

### Calendar, reminders, tasks and alarms

Calendar uses Android CalendarProvider via `AlphaCalendarPlugin.java`; reminders are device-local, using `DailyApps`/native receivers and alarm scheduling. Existing tests cover selected ranges, some recurrence/time-zone cases, reboot and notification actions. The new workflow Calendar read is explicitly selected and bounded, but it is not a cloud-calendar sync service. A phone-only calendar cannot be queried while the phone is powered off unless selected data was synchronized or a hosted account grants access.

The initial audit found missing deletion; a revision-bound native inspect/edit/delete boundary and direct Delete event UI are now implemented. Direct mutations cover product-owned local timed events without recurrence, attendees or alerts; complex/external events retain an Android Calendar handoff. Native acceptance is still in progress: Build84 reached delete review, but the fixture failed to match Android’s button casing; the fixture correction awaits its next run. Canonical chat operations still need generic Calendar CRUD registration and durable receipts. Reminders use inexact `setAndAllowWhileIdle` with Done-driven recurrence. A reviewed Clock set/show/snooze/dismiss bridge is now implemented; intercepted-intent tests pass both variants, while actual ringing remains unverified. AOSP Clock may ignore requested snooze duration and affect all ringing alarms, which the updated review explains. The upstream native-calendar, native-reminders and native-eliza-tasks packages inspected are Apple-specific, so Android implementation must be ported and qualified rather than assumed available.

Required calendar journey: select a calendar, query actual availability, review title/start/end/time zone/all-day state, create/edit/delete exactly the selected event, refresh provider state, and recover from revocation or concurrent changes. Recurring-series versus single-occurrence edits must be explicit. Required task journey: create, edit, complete, snooze, reopen/delete and survive reboot; define overdue handling and time-zone changes. Required alarm journey: actual ringing, dismiss/snooze, sound/vibration/DND behavior and reboot/reschedule, or an explicit native Clock handoff whose result is not represented as an app-owned alarm. A scheduled notification is not proof of a wake-up alarm.

Use native CalendarProvider and AlarmManager where appropriate; use the existing elizaOS scheduling/workflow services for hosted execution. Specify recurrence, DST gaps/folds, overlap, catch-up and cancellation consistently. See the official [calendar provider](https://developer.android.com/identity/providers/calendar-provider) and [alarm scheduling](https://developer.android.com/develop/background-work/services/alarms/schedule) guides. Exact-alarm authorization and device policy must be read back on the actual image.

### Notifications and reconnect delivery

Own-app channels and native tap actions have focused passes. Cross-app collection now has explicit Android access, selected app/signature policy, redacted previews, encrypted metadata history and mock-mode pause, but its latest native attempts fail before exercising the flow because System UI displays an ANR dialog. The retained trace identifies System UI startup blocked in SurfaceComposer GPU-context retrieval; this is not a notification-feature pass.

For MVP, prioritize own-agent results, reminder/task actions and a durable in-app result inbox. Cross-app notification mirroring (engineering disposition, October 7) stays implemented but strictly opt-in and off by default, outside onboarding, limited to user-selected apps with previews hidden when locked, clearly disclosed, and not an MVP acceptance gate; re-evaluate before any Play Store distribution. Required states include denied channel permission, muted channel, locked screen, tap after process death, duplicate delivery, cleared history, account switch and stale action. Hosted results must persist independently of push delivery. Reconnect uses a cursor/acknowledgement and retrieves missed results once. A WebSocket alone cannot satisfy powered-off-phone delivery. Android's [notification permission](https://developer.android.com/develop/ui/views/notifications/notification-permission) and [NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService) are distinct capabilities and require separate qualification.

### Hosted workflows and daily digests

The phone now has typed New/edit, owner/version-bound save review, durable ambiguous-save recovery and exact-run foreground phone approvals. Frozen runtime patches through0012 pass full repository verification and actual HTTP/PGlite/Smithers tests. Notify/Speak and immutable compiler-upgrade compatibility exist as later isolated patches, not the running/deployed product. The development launcher explicitly disables scheduling and personal-assistant defaults. Civil scheduling, deployed digest templates and powered-off/reconnect evidence remain incomplete.

The MVP does not require exposing every workflow programming primitive. It does require working morning and evening digest/task loops. Implement these as parameterized upstream templates using generic read, compose, approval, notify and durable-result primitives. Inputs are selected accounts/calendars/tasks, time zone, schedule and delivery preference; no hardcoded fictional people, addresses, app names or fixed device IDs. If a step needs an unavailable phone, record waiting/unavailable and run the hosted portions; do not fabricate device data. At least two loops must actually execute with the phone powered off and their results arrive once on reconnect. Manual execution while the phone is online does not meet that criterion.

### Browser and password manager

Current browser code is a Chromium-powered Android child WebView with Alpha-owned chrome. It has bounded native tabs/navigation, profile handling, selected file handoffs, share and reviewed read-aloud implementations, plus focused earlier browser tests. It is not Chrome or a full AOSP Chromium browser distribution. Chromium's [WebView architecture](https://github.com/chromium/chromium/blob/main/android_webview/docs/architecture.md) explains the content-embedding boundary; Chrome profile/password UI and agent automation do not appear automatically.

Required browser MVP: enter/search URL, accurate origin/security state, back/forward/reload, tab close/restore policy, a persistent sign-in profile with an explicit ephemeral private-tab option (October 7 decision), permission prompts, downloads/uploads, external navigation and return, useful explicit agent page assistance, and provider-backed login. Remote pages must not receive the Capacitor bridge. Content passed to an agent is selected/reviewed and excludes credentials, hidden fields, frames and private form values. The new conservative extractor rejects known credential-provider URLs, sensitive route/DOM/text markers, authentication-like numbers, and over-budget documents before issuing a reading token. Both native variants passed blocked-page zero-outbound tests plus an approved ordinary-page synthesis/playback flow. It is not a universal secret classifier: arbitrary unlabelled secrets, languages and page-world API tampering remain limitations. An isolated-world patch is staged, but installed Chromium138 lacks the required runtime feature; provider upgrade and adversarial native qualification remain open. Future summarization must reuse the qualified boundary. Navigation or origin changes invalidate old actions. Agent assistance must not claim arbitrary purchasing/booking works merely because the page renders. See [Android WebView bridge guidance](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges).

October 7 owner decision: an integrated password manager is in scope as a reusable elizaOS upstream component consumed by Alpha; unmodified Proton Pass remains an optional alternative provider, with Alpha-owned setup/status. Android does not let an ordinary app override the user's autofill choice; installation is not enablement. Proton account setup, provider selection and vault unlock remain user/provider-owned. See [Android autofill](https://developer.android.com/identity/autofill/autofill-optimize) and [Proton Android setup](https://proton.me/support/pass-setup-android). Image provisioning can preinstall a provider, but must not be described as bypassing vault unlock or ordinary permission policy.

Password autofill remains an MVP acceptance gate; passkeys are deferred outside MVP under approved #402. The following provider research informs a separate post-MVP qualification. Proton documents Android14+ third-party passkeys; WebView browser-mode credential support is feature-detected and requires appropriate provider authorization of the browser identity. There is no evidence the actual Alpha release certificate/package is authorized. See [Proton passkeys](https://proton.me/support/pass-use-passkeys), [WebView credential integration](https://developer.android.com/identity/sign-in/credential-manager-webview), and [privileged callers](https://developer.android.com/identity/sign-in/privileged-apps). A synthetic autofill test cannot close real-vault/passkey acceptance.

Keep provider source/license separate: Proton Android is GPLv3-or-later, not an MIT component to paste into Eliza. Generic interfaces can be upstream MIT while the provider remains a distinct app. See [Proton source](https://github.com/protonpass/android-pass). The development emulator's test-signed WebView does not qualify the final image: choose a maintained stable provider, release signing and update owner, and test the production `user` image. [Chromium AOSP integration](https://chromium.googlesource.com/chromium/src/+/HEAD/android_webview/docs/aosp-system-integration.md).

### Email and messaging

The active app has encrypted local draft recovery and a Cloud protocol, but real Gmail grant exchange remains failed. Local drafts are not Gmail drafts, and a generic `{ok:true}` from a connector is not a durable provider send receipt. An isolated Inbox foundation now adds owner/grant-bound operations, MIME review, provider draft/label operations and unknown-result handling; it is not applied or deployed. Attachments and phone-side durable review remain incomplete.

Email is MVP (owner decision, October 7). Require real connect/revoke, thread paging, inert message rendering, explicit attachment access, reply recipient/account review, draft save, send result with provider identity, archive/trash/undo and response-loss recovery. Do not retry an ambiguous send automatically. Keep tokens server-side in managed grants; expose owner-bound operations to any Eliza client. Telegram/Discord are deferred; if later restored they should use their existing generic provider plugins, not phone-specific integrations.

Some constants should remain constants: protocol versions, bounded payload limits, allowlists and model hashes can be security/reproducibility requirements. Change them through versioned capabilities and explicit configuration, not unrestricted user strings. Product branding, icons, routes and layout belong in Alpha; reusable semantics belong upstream. Publish reviewed upstream commits, update submodule and lock together, and retain source/license notices. An unmerged patch directory and a local root check are not public upstream contribution or reproducible clean-clone delivery.

## Private hosting and physical acceptance

An enclave-hosted agent that calls Cerebras is not evidence that model inference ran inside Alpha's TEE. Current development routing explicitly uses direct Cerebras. Retain that user-requested route, but describe the actual data boundary and separately resolve the DoD's private-TEE-inference requirement. Attestation verifies measured enclave identity; it does not attest an external provider's inference execution. [AWS attestation documentation](https://docs.aws.amazon.com/enclaves/latest/user/set-up-attestation.html). Never weaken the existing signing/KMS policy to make a deployment test pass.

The image/hardware work needs the exact unlockable Pixel SKU, Android/device-tree/vendor inputs, signing and recovery path. APK HOME-role tests are not a full AOSP/Lineage image boot. A stock emulator's API35 geometry is not Pixel10 hardware evidence. Android's [device build identifiers](https://source.android.com/docs/setup/reference/build-numbers) and [flashing guide](https://source.android.com/docs/setup/test/running) are starting references, not confirmation of a particular purchasable SKU or device image. Qualify the actual chosen device before committing to provisioning four units.

Remaining DoD delivery gates: five-minute unedited physical-device demonstration; setup and reproducible build/deployment instructions exercised by another engineer; live paired hosted agent on each of four devices; successful offline-phone loops/reconnect recording; stability pass and agreed P0/P1 closure; source/license delivery; stakeholder demonstration and follow-up. Do not mark these done from CI, a health check, or this report.

## Recommended immediate priorities

1. Freeze a written MVP profile and comment out known deferred feature entry points with restoration notes; reconcile the remaining speech/local-inference question and powered-off scheduling (A-09); messaging scope was decided October 7.
2. Complete one real Cloud/remote session on the phone with voice, note/calendar/reminder actions, interruption and restart. Keep local development as a diagnostic path.
3. Make two hosted digest/task loops run independently of the phone and deliver durable results after reconnect; this is the largest missing functional acceptance proof.
4. Qualify browser/password-provider and on-device speech on the actual target image; measure latency honestly.
5. Consolidate reusable semantics upstream while preserving Alpha UI, then deliver reproducible images, four devices and the acceptance package.
