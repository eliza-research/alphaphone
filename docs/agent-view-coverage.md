# Agent context coverage by view

Current-source corrections (October 8, from `runtime/device-actions.ts`, `runtime/connection-ui.tsx`, `runtime/phone-context.ts` and the camera adapter) are in the next section and override older statements on this page. Initial source audit: Build 49 on 2026-09-30. Updated from archived Build 51 real local-agent evidence below; Build 52 native-video context execution remains pending. This documentation update performs no runtime operations. Root-view coverage does not establish every selected object, overlay or Cloud/enclave flow. Mock and visual-fixture mode do **not** install these production adapters (`main.tsx`); their simulated agent presentation is not evidence of native integration.

## Shared contract and actual action boundary

[agent-adapter.ts](../apps/app/src/prototype/agent-adapter.ts) derives context from `shell.S().view || 'home'` and updates it after component updates. [alpha-client.ts](../apps/app/src/runtime/alpha-client.ts) assigns a revision, cancels an active request and clears proposals when view/selection/sensitivity changes; Back/HOME and disconnect also cancel. A connection-session change clears visible chat/draft. [phone-context.ts](../apps/app/src/runtime/phone-context.ts) sends only an allowlisted view, revision, sensitivity=false and optional bounded opaque `{kind,id,revision,accountId}`. It rejects sensitive screens and unsupported kinds; it does not serialize selected text, images, audio, URLs, geographic coordinates, query strings, account credentials or arbitrary object fields.

For remote/local and shared/dedicated Cloud chat, the current-turn observation is embedded explicitly as **untrusted client-reported data, not device permission**, followed by the unchanged user text. Metadata is also supplied; shared Cloud's runtime route ignores that metadata, so the text envelope is the common model-visible contract. An ID alone does not let the model read the corresponding object. User-entered message content is sent intentionally; the context exclusion does not redact text the user chooses to send.

**Current operation set (October 8 source).** `validateDeviceOperation` in `runtime/device-actions.ts` admits these typed operations, each only after explicit approval bound to owner, agent, device, current context and proposal expiry, with a native journal reservation before the effect and a durable receipt after it:

- Legacy common operations: `create_note`, `create_reminder`, `open_view` and `browser_navigate` (exact HTTPS URL without user information).
- Notes: the selected-note operations in `runtime/notes-contract.ts` and the local `notes_query` lookup (`notes.query.v1`), which shares only the note the user then chooses.
- Reminders: create (`reminders.create.v1`) and the selected-reminder operations in the upstream reminder contract.
- Calendar: local event creation, next-event read and selected-event operations from the upstream calendar contract (`calendar.local-event.v1`; `calendar.create.v1` and `calendar.next-read.v1` on Android only).
- Maps: the selected place or route read (`maps.selected-read.v1`); it shares location information and never starts navigation.
- Clock: a reviewed handoff to Android Clock (`clock.handoff.v1`, Android only); the handoff result is a dispatch receipt, not confirmed alarm state.
- Workflow steps: `read_selected_notes` and `read_calendar_range` reads, plus `post_notification` and `speak_text` presentation, only inside a reviewed workflow execution.

A capability is used only when the connected runtime advertises it. Permitted `open_view` destinations are home, reminders (shown in Calendar) and the enabled MVP views: notes, browser, calendar, files, photos, camera, maps, inbox, workflows and settings. Phone, Messages, Contacts and Wallet are deferred MVP views, and `open_view` refuses them in every build, including development builds made with `ELIZA_DEV_ALLOW_TEST_MOCKS=1` (`runtime/device-actions.ts` admits only enabled MVP views); fixture use of those views is not product scope.

**Connections.** Resident, remote and local connections negotiate verified phone actions during enrollment. A Cloud agent connection also enrolls this device and gets verified phone actions when the Cloud runtime advertises the device-action protocol and the owner identity matches. Otherwise it stays chat-only and shows that phone actions, workflows and paired speech are not enabled. UI buttons for native app operations are separate direct user actions, not extra model capabilities. No free-text response is parsed as a command.

## Historical Build 49 findings versus intentional limits

Items 1–3 below were identified before the Build 50 source corrections. See corrections and Build 51 evidence below; the historical text is not current unresolved status.

1. **Concrete correctness bug: selected video blocks otherwise valid chat.** `camera-adapter.ts:79` emits `{kind:'video'}`, while `phone-context.ts:5` omits `video`. Opening a native video and sending through remote/Cloud throws “This selected object cannot share agent context.” Add a bounded video identity kind or deliberately map it to an agreed media kind, then test captured-video → chat → selected-ID envelope and leaving/revocation. No source fix was made in this audit.
2. **Missing selected-workflow binding.** A real workflow detail/run is visible, but context remains only `workflows`. A user asking about “this workflow/run” cannot identify it. Add an opaque ID/version plus account/session binding after defining the observation contract; preserve source/output exclusion. This is a missing integration, not evidence that runtime management buttons are fake.
3. **Overlay/background privacy lifecycle needs an explicit contract/test.** Context ignores `s.screen`, chooser-open state and document visibility; agent adapter has no visibility/pagehide listener. Ordinary prototype lock can preserve a previous selection/proposal revision, and opening a credential chooser does not suspend an in-flight request. This does **not** expose screen text under the current identity-only envelope, but does not satisfy a blanket “observation pauses on lock/credential surfaces” claim. Define pause/invalidation for actual native background/lock and credential overlays, then verify stale proposals cannot execute after returning without review. Keep ordinary chat-sheet preservation intentional.
4. **Folder, notification, phone/message and settings-detail context is incomplete.** They emit generic view only; declared allowed kinds do not prove there is an emitter. Missing content/action providers should stay honestly unsupported rather than infer arbitrary strings as authority.
5. **Cloud phone actions (historical Build 49 finding, since changed).** At Build 49 the Cloud active type had no `DeviceActions`. Current source enrolls the device with a Cloud agent and negotiates verified phone actions when the Cloud runtime advertises the device-action protocol; a runtime without it stays chat-only. Live Cloud device-action acceptance remains open.
6. **All fourteen views have a generic context route, not fourteen live integration passes.** Live local evidence explicitly covers Notes/context and the bounded action slice. Maps has a targeted renderer observation test; inbox has lifecycle fixtures. No existing single test proves all native-selected kinds, overlays, account changes and real model replies end-to-end.

## Minimum next verification

After coordinated source fixes, use one authenticated local session and repeat against actual Cloud/enclave when authorized: navigate each row, open a real fixture selection, send a harmless “identify my current view and opaque selected ID; do not perform actions” request, compare the transmitted bounded envelope and model response, then change selection/view/account and verify cancellation/stale-approval refusal. Add positive/negative coverage for video, workflow/version, folder selection, sensitive wallet/secure lock and credential-overlay/background transitions. Explicitly verify no body/URL/coordinates/credential fields appear in observation metadata or envelope. Preserve separate user-approved content-sharing and effect tests; do not add autonomous side effects to this context audit.

## Build 50 source corrections (not APK acceptance)

The findings above describe the pre-fix Build 49 source audit. The next candidate now includes `video` in `phone-context.ts`'s bounded identity allowlist. No image/video bytes, content URI, caption, filename, or other arbitrary media fields are retained. The camera adapter's existing real provider selection is unchanged. The remote transport (`remote-protocol.ts:224`) sends metadata without a second selected-kind enum; upstream `packages/agent/src/api/chat-routes.ts:2174` reads object metadata and enriches declared UI view fields, without rejecting `video`. `conversation-routes.ts` passes this to generation. The legacy development gateway (`scripts/dev-agent.mjs:231`) checks bounded identifier syntax rather than a selected-kind enum. The existing model-visible observation envelope also carries this identity for Cloud shared hosts that ignore metadata. No upstream schema patch is needed for video.

`agent-adapter.ts` now reads the workflow adapter's authenticated, session-bound `workflowSelection()` getter. Only workflow ID and version are included, not code, run output or credentials. Chooser-open, `document.hidden`, pagehide, and verified prototype `screen === 'lock'/'off'` states now suspend context. This increments the existing context revision, cancels pending client turns and clears proposals while preserving the connected transport and conversation history. Closing/foregrounding permits a new explicit turn; stale responses are discarded. Document visibility and prototype screen state do not establish native Android Keyguard state. Cancellation remains best effort for already dispatched server work or committed native effects.

`node scripts/test-agent-context-browser.mjs` passes against a **fresh dedicated local Vite process** with actual production renderer/adapters and synthetic AlphaPhotos/agent boundaries. It opens the video tile and Ask Alpha sheet, sends through the actual composer, verifies only opaque video ID/revision reach the observation, then exercises chooser, visibility, and pagehide cancellation. It verifies blocked sends while suspended, expired proposals, stale reply suppression, retained prior messages/session and successful fresh requests. Seven outbound synthetic requests are expected; no native capture, model call or Cloud acceptance is claimed. `npm run typecheck` passes. Real native per-view tests and APK verification remain separate. Do not reuse an HMR-modified Vite process: timestamped imports can create a second controller instance in a test's dynamic imports.
