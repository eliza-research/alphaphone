# Alpha and Eliza unification audit — 2026-10-27

## Decision and target

Alpha should become a branded build of one upstream Eliza mobile application. Shared ownership must cover the launcher, domain views, agent client, context selection, action contracts, native adapters, local inference, and AOSP target. Alpha retains its character, visual theme, app identity, signing configuration and installed-data compatibility identifiers. These identity fields are necessary even when visible differences are aesthetic.

This report precedes implementation. It is based on direct source inspection, not product acceptance. The initial checkout is Alpha `417f8196e` with Eliza `ff9c8264550efd64fd0119c6ff50f99eb8561977`. Implementation starts from the existing combined PR #624 head `ecd5e30ef4fc3d66f4ed43c0ae58502b8fb96b99`, with Eliza `4b928290d388e8f9866b6c404a1b186c7bfe7f70`, so the existing consolidation stack is retained. Findings must be checked against that candidate before edits; the inventories below describe the initial checkout.

## Migration order

1. Land small, independently verifiable shared primitives and remove their consumer duplicates. Preserve public behavior and existing data.
2. Correct the common native inference profile and unify model lifecycle, capture, playback and cancellation. Measure model loads, PSS, first audible latency and long-session growth.
3. Upstream owner-bound native services: auth, provider transport, media/files, browser lifecycle, telephony journals, notifications and reset. Keep package/store migration data explicit.
4. Build one mobile shell from upstream domain components and Alpha's missing capabilities. Parameterize theme and persona; use that entrypoint for both products.
5. Move Pixel 10a source admission, listener and image integration upstream and align privileges. Qualify standalone/launcher debug/release separately from full AOSP boot.
6. Remove remaining Alpha implementation only when both brands execute the same acceptance paths. Keep a shrinking inventory; do not rename a copied fork and call it unified.

## Completion criteria

The goal is incomplete while either app retains a separate behavioral implementation, the native profile uses a second local-model stack, or Pixel 10a is not a common upstream target. Full completion also needs real native speech/context performance measurements, both Android distributions, full image boot and device/user acceptance. Missing credentials, qualified model inputs, signing or device access must be recorded as unavailable evidence; they cannot be replaced with synthetic success.

# Alpha/Eliza renderer consolidation audit — 2026-10-27

Scope: read-only audit of Alpha's tracked renderer, its upstream staging boundary, and the pinned `vendor/eliza` app/UI/plugin implementations. No source edits, source build, device tests or live integrations were performed by this audit. Alpha current pin is `ff9c8264550efd64fd0119c6ff50f99eb8561977` as admitted by `scripts/prepare-client-features.mjs`.

The user's new direction supersedes the older documentation's separate-renderer ownership: one functional Eliza mobile application, with Alpha supplying branding/character/package identity. Existing user-data namespaces and Android identity must survive that ownership change.

## Size and central finding

`apps/app/src` contains 424 readable text files / 54,279 lines (including JSON, styles and fixture text; excluding binary images/fonts). Groups: `prototype` 92 / 26,976; `runtime` 156 / 19,337; `browser` 140 / 5,522; `maps` 21 / 797; `passwords` 2 / 348; root 13 / 1,299. Large files are `prototype/model.js` 5,714 lines, `template.html` 4,426, `runtime/connection-ui.tsx` 2,736, `prototype/agent-adapter.ts` 1,417, `voice-adapter.ts` 1,164, `camera-adapter.ts` 1,001, `inbox-cloud-adapter.ts` 874 and `settings-adapter.ts` 799. These are the core reason Alpha is not thin.

The pinned upstream `packages/ui/src` is 2,240 readable files / 558,968 lines (many tests, stories, eight large locale files and Cloud surfaces), and `packages/app/src/renderer` is 26 files / 18,365 lines. Moving Alpha directly to the full UI barrel would introduce large unrelated dependencies. The right target is a stable mobile-shell entry and shared domain-view entries, with lazy domain loading.

I found 128 explicit upstream import/re-export statements in 73 Alpha source files. A byte-hash comparison of nontrivial Alpha TS/TSX/JS/MJS/CSS files against upstream found no byte-identical complete files: most previous straightforward copies were already replaced by wrappers, while the remaining duplication is behavioral and architectural.

- `scripts/prepare-client-features.mjs` authenticates upstream bytes, copies them outside the immutable submodule to `.eliza/client-features`, and emits a complete source receipt. `vite.config.ts` supplies narrow leaf aliases. Retain source authentication while improving the upstream public API.
- Files/scanning: `browser/files.ts`, `file-archive.ts`, `scan-correction.ts`, `scan-draft.ts`, `scan-edges.ts`; `prototype/{local-ocr,scan-links,scan-pdf,scan-text-layer}.ts`; `runtime/inbox-attachment.ts` already use `plugins/plugin-files` implementation. Remaining Alpha review/layout adapters are not already shared.
- Maps: 19 imports/re-exports across `maps/*` use `plugins/plugin-maps/src/client` (state, plane, native location, route distance, regional provider, saved places, navigation voice, navigation relay, selected context and sharing). Alpha's 797-line Maps directory is already comparatively thin, but the 496-line `prototype/maps-adapter.ts` remains a separate view.
- Notes: `runtime/{notes-store,notes-secure-store,browser-notes-document,notes-contract,note-dates,notes-trash-policy}.ts` and query/trash adapters already consume `plugins/plugin-notes/src/client`. Retain encrypted-data and conflict behavior when replacing presentation.

## Import/API problems blocking a thin wrapper

1. The consumer still knows dozens of private upstream paths. Publish stable leaf entry points for resident client, observation, device-review models, maps, files, notes and a native mobile shell; avoid root UI barrel imports in capture and background code.
2. `prepare-client-features.mjs` currently hard-codes one upstream pin and hashes for four voice inputs. It rewrites session fetch, extracts a type union and logger types, deletes logger, and generates Alpha-named protocol/type adapters (projectionVersion 7). A normal pin update can stop here even if interfaces remain compatible. Upstream a browser-safe voice entry requiring an injected fetch and lightweight protocol/logger dependencies; then delete consumer source projection. Removing the guard without fixing the import closure is not equivalent.
3. App root supports web/desktop/iOS/Android/Cloud and uses a very wide `@elizaos/ui` barrel. A mobile resident/AOSP composition entry must avoid loading Cloud admin, wallet, desktop, agent-host purchasing and other unused surfaces. Keep runtime feature/profile selection upstream and Alpha theme-only.
4. The prototype model registers and mutates many views globally. Feature migration should replace one complete domain at a time with an upstream module and eliminate its old registration/adapter; otherwise both paths keep executing and registering listeners.
5. Alpha and Eliza must share same feature decisions for alarm ownership, Google/Calendar sync, mail composing, native speech, reset and AOSP telephony. Existing documentation describes real conflicts, not aesthetic differences. The user's direction authorizes resolving those upstream, but a file move alone cannot prove parity.

## Proposed migration order and evidence

1. Record the shared AOSP/mobile profile, brand schema, app identity and old storage namespaces, canonical view/action IDs, and explicit legacy migrations. Pin one reviewed upstream implementation; no edits in `vendor/eliza`.
2. Consume already-shared leaf helpers (PCM encoder first; then capture, transcript guard, turn and JSON client when full contracts fit). Close voice source projection upstream. These are scoped deletions with existing contract and browser tests.
3. Upstream missing domain behavior from Alpha: local editable/voice Notes, Calendar local/linked controllers, Gmail draft/compose/attachment lifecycle, Photos/scanner reviews, workflow notices and capability-safe native actions. Test in upstream AND Alpha before replacing views.
4. Create mobile resident shell using existing upstream Home/launcher, ChatOverlay, context/agent-surface registry and lazy plugin views. Apply Alpha theme to same components. Eliminate prototype model/template/adapter registration only when no functional feature remains behind it.
5. Resolve Clock/AOSP feature parity and update action/view aliases and stored references through explicit migrations. Keep receipts and provider effects intact; do not reissue old sends or approvals.
6. Verify both themes against one behavioral scenario suite: cold start/sign-in/account changes; local agent restart; current context; text send/stop; local STT/TTS and barge-in; every action review; offline handling; native Notes migration; Calendar timezones/recurrence; attachment bytes; SMS receipts; reset/listener; portrait/landscape/large text/keyboard/TalkBack.
7. Run `npm run verify`, all four distribution APK builds/inspection, upstream package tests/typecheck/lint/verify, renderer visual audit and desktop/mobile captures, then actual emulator HOME, full AOSP image boot, Pixel 10a and real provider/device acceptance as separate evidence. A successful source build is not full AOSP or physical parity.

## Completion criteria

Alpha functional directories should disappear or become generated immutable upstream imports. Its remaining hand-authored production code should only select common shell/profile/theme, preserve product registration and consume the pin. Both brand builds must report the same functional feature manifest and canonical action list. Shared tests and end-to-end acceptance must establish behavioral parity, and source admission must prove that the code in both distributions is the same reviewed upstream implementation. # Alpha/Eliza agent, context, tools and runtime audit

## Findings in brief

The remaining large independent layer is the host/client: it duplicates connection coordination, transport parsing, native executor orchestration, record approval/recovery, Google service composition, workflow authoring/protocol and most feature views.

## Discrepancy and consolidation matrix

### 1. Native Cloud binding picks Cloud embeddings in the native profile (high priority)

- Alpha: `android/app/src/main/java/ai/elizaresearch/alphaphone/LocalAgentProviderAdmission.java` `applyProviderEnvironment` always sets `ELIZAOS_CLOUD_USE_EMBEDDINGS=true`, `ELIZA_DISABLE_LOCAL_EMBEDDINGS=true`, `ELIZA_LOCAL_EMBEDDING_ENABLED=0` for `elizacloud`.
- Alpha: `AlphaLocalAgentPlugin.java` `configureEnvironment` calls `configureLocalEmbeddings` only for an absent/non-Cloud provider. It does not inspect `BuildConfig.ELIZA_RUNTIME_PROFILE` at this decision.
- Alpha: `backend/native-cloud-runtime-config.ts` explicitly adds a Cloud embeddings service route only in the `cloud` profile, which is better scoped than the Java environment and should become one canonical profile contract.
- Shared engine: upstream `plugins/plugin-native-inference/src/aosp-local-inference-bootstrap.ts` handles local BGE through libelizainference; `ElizaAgentService.java`, `BgeEmbeddingSession.java` and the packaged BGE model already exist.
- Recommendation: create one shared Android host inference policy, with Cerebras text through owner-bound Eliza Cloud in both products and local libelizainference embeddings/STT/TTS in native/AOSP. Keep explicit Cloud QA only as an opt-in if the new owner intent retains it. Do not silently fall back to Cloud if native assets are missing; surface unavailable and keep qualification gates.
- Verification: inspect generated env/route config for unbound, native+Cloud, native+direct diagnostic, explicit Cloud QA and account changes; run existing local embedding bootstrap/provider-admission tests and real ABI embedding smoke runs separately from APK build.

### 2. Alpha has separate development action names (small but real divergence)

- `backend/proposal-action.ts` registers `CREATE_NOTE`, `CREATE_REMINDER`, `OPEN_VIEW`, and returns `actionName: PREPARE_ALPHA_ACTION`; the last action name is not even one of its exposed tool names.
- `backend/runtime.ts` filters assistant actions down to REPLY/IGNORE/NONE, adds the three Alpha proposals, removes embedding handlers and supplies a product-specific character prompt.
- This is a deliberately limited development host, not the production resident. Production should not be described as having these separate actions.
- Upstream convention: `PROPOSE_DEVICE_ACTION` with `create_note`, typed reminder operations and canonical navigation `VIEWS`/`VIEWS_SHOW`.
- Recommendation: make development exercise the same resident/device action service with a deliberately non-effecting executor, or retire the diagnostic host where no longer used. Do not merely rename CREATE_REMINDER: its wall-clock+timezone shape differs from the legacy upstream dueAt and modern typed reminder_create contracts. Reuse upstream reminder input resolution. Keep fixture/no-effect guarantees explicit.
- Tests to migrate: `backend/test-runtime.ts`, `scripts/dev-agent.mjs`, `scripts/test-dev-agent.mjs`, development proposal fixtures. Live provider evidence must not be replaced with mocks.

### 3. Device executor orchestration is large and Alpha-owned (high-value shared extraction)

- Alpha: `runtime/device-actions.ts` defines its own `DeviceActions`, pending/review parsing, capability checks, approval/claim/result/receipt coordination, durable local journal recovery, context binding and notices (578 lines).
- Eliza owns the server half in `plugin-assistant/.../device-actions/{service,contract,action,effect-receipts,read-completion,workflow-service}.ts` and Android execution adapters.

Hosts inject authenticated request, store, clock, native executor, foreground-review presenter and product configuration. The implementation must distinguish a reserved proposal from dispatched effect and preserve unknown outcomes; do not replace journaling with a plain fetch client.

- Foreground review functions and `NamedTargetValidators` currently repeat upstream `foreground-review-contract.ts`; split pure types/parsers to `packages/contracts` so both clients import them without importing server crypto/service code.

### 4. Clock core validation is duplicated (low-risk early consolidation)

- Alpha: `runtime/clock-contract.ts` reimplements time zone validation, object/exact keys, Clock day sorting, typed operations/result handling and observation checks (~200 lines).
- Upstream: `plugin-assistant/src/services/device-actions/clock-contract.ts` already owns the wire contract and includes both external handoffs and owned alarms.
- Existing Alpha policy: supports handoffs, not owned alarms; refuses `days: []` while upstream accepts it as explicit one-off; Alpha app Clock title/copy does not prove ringing.

Leave the Alpha draft/form and product-specific review text in a tiny presentation wrapper. Tests already cover exact shapes, day order, duplicate days, time zones and unknown handoff outcome.

Host injection includes credential reference access, allowed service origins, runtime bridge, app view catalog and renderer lifecycle hooks. Configure display branding and installed namespaces independently.

## Context size and inference latency assessment

### Confirmed source behavior

- Native plain-text protocol is already negotiated: `connection-ui.tsx` uses `nativeProse = isAndroid && selected.kind==='resident' && selected.userTextFormatVersion===1`. It then sends authored `text` unchanged with `clientDevice.context` metadata and `userTextFormat: plain-v1`.
- Legacy/non-native hosts receive `phoneContextMessage`'s 7-line instructional envelope plus the same context in `metadata.clientDevice.context` and `metadata.alphaPhone.context`. This duplicates the observation and repeated policy in persisted dialogue. Do not claim the current native route always suffers that duplication.
- Upstream `context-assembly.ts` excludes RECENT_MESSAGES provider text when structured dialogue exists, specifically to avoid duplicating history. It also substitutes a provider reference for a duplicate Clock snapshot. These are good patterns to reuse, not replace.
- The upstream authenticated-phone-capability instruction is assembled on every device turn, independently of whether a phone operation is asked for. Its source has about 6,598 literal characters across capability branches (~1,650 tokens at a crude 4-char estimate; actual active output depends on enrolled capabilities and tokenizer). PROPOSE_DEVICE_ACTION's description starts with ~4,113 literal characters (~1,028 estimated tokens) before appended Clock/foreground constants and full operation schemas. The schema is partly filtered by capabilities but the broad phone description repeats much of the active capability instruction.
- `deviceActionForCapabilities` removes unsupported branches and duplicate owned-vs-handoff Clock guidance. Preserve and extend that capability filtering rather than exposing all tools on every turn.
- Alpha `ServiceReadCache` already has 24-entry/4 MiB/30-day local bounds, account ownership and CAS; it does not grant write authority. Subscription authorization refresh is async by contract and should not be reintroduced on the chat critical path.
- `createManagedGoogleAgentHost.verified` performs `identity`, `gmailAccounts`, the requested operation, and `gmailAccounts` again for each tool call, with repeated local credential comparisons. That is at least three metadata/service requests beyond the operation; it can dominate multi-step Google turns. Reads inside `calendarSources` perform another account request.

### Consolidation/performance changes worth measuring

1. Use one canonical plain-text + typed metadata ingress in both launchers. Retain legacy envelope parsing only for old stored messages and negotiated older clients, with an explicit compatibility path. Never rewrite stored user-authored prose or silently discard historical content.
2. Keep the minimal capability/authority boundary once, then expose operation documentation through existing `DISCOVER_ACTIONS`, context catalog and exact shared schemas only when needed. Remove duplicate explanatory prose, not permission checks or source evidence. Compare prompt tokens and successful action rates before/after.
3. Cache stable schema/capability descriptions by immutable enrollment/view-profile revision. Move invariant prompt material to a stable prefix so provider caching can work. Keep current selected-object observations dynamic and small.
4. Extract local credential/account generation binding from the protected native admission and reuse that identity across a turn. Consolidate redundant Google identity/list calls while retaining revocation, grant freshness and exact prepare/dispatch checks at actual effects. Benchmark before removing any network check; no blanket indefinite auth cache.
5. Native profile must use the already packaged libelizainference BGE slot. Measure actual embedding latency and memory on both ABIs, request/cancellation sharing with STT/TTS, and Pixel thermal/memory behavior. Model packaging or a successful Java test is not performance evidence.
6. Preserve full authorized context and retrieval completeness. Upstream AGENTS explicitly forbids silent truncation, summaries and recency caps. If a model capacity limit is reached, surface the limit and preserve pending work; optimization must remove duplicated/system material and reduce unnecessary I/O rather than silently dropping content.

No live model timing was measured in this audit. Token figures are source-character estimates, not benchmark results.

## Inference and performance findings

1. **Already one engine family, not yet one lifecycle.** App speech/embeddings, bionic resident ASR and listener all use libelizainference. However, `AlphaParadeeSpeech` uses two native contexts; `AlphaLiveVoiceCapture` keeps a separate static VAD-only native context; bionic uses its own resident context; the separate listener owns another ASR model. Share contexts within an owner/process where appropriate, and preserve isolation across the separate listener. Do not claim measured RAM savings before recording PSS/model load count on the target.
2. **Do not load both ASR and TTS for a simple status probe.** Alpha's `localEngine.use` lazy wrapper instantiates `AlphaParadeeSpeech`, whose constructor opens both models. Upstream `InferenceSession` does not load a model in its constructor. Migrating to it permits capability/status checks without eagerly loading unrelated weights, provided ready means inputs/backend are actually admitted.
3. **Keep renderer PCM out of the normal path.** The direct native owner-bound PCM route already exists. Remove renderer-forwarding compatibility only after both launchers build with the shared capability and installed transport tests pass. Silent fallback/replay after error would duplicate audio and break cancellation.
4. **Bounded playback is good shared infrastructure.** Alpha's 30-second SpeechPcmQueue, callback backpressure, zeroing, explicit streaming-failure behavior and immediate cancellation should move upstream intact. The main latency and quality comparison must include endpoint delay and first audible output, not just cloud token time.
5. **Text/cloud policy remains separate from local models.** Native production uses Cerebras through authenticated Eliza Cloud, with Paradee + Phonon + Silero local. BGE is packaged and available, but ff9c826 routes Eliza Cloud-bound embeddings to Cloud, contrary to the desired all-local-models policy. PR624 fixes this through the native profile and canonical service routing (below). Cloud QA uses Cloud embeddings/STT/Cartesia and packages no local models. Shared profile selection must make this same distinction; neither profile should silently replace the other.
6. **No evidence of optimal inference yet.** Source has timing instrumentation and current component corpora; installed streaming/cancellation, hardware input/output and end-to-end p95 remain unqualified. Run cold/warm model loads, PSS before/during/after, long-session context size/latency, word-error corpus, interruption, Bluetooth/call/focus, and peak-memory traces on the actual Pixel target. Existing source explicitly requires these gates.
